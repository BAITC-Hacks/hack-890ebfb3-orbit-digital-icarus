## Real collaboration acceptance

`tests/e2e/community.spec.ts` opens independent browser cookie jars, not mocked users:

1. Anonymous browsing works; event creation and event API access require login. Public source matching still returns three real cards without an account.
2. A provider signs up and publishes through the UI. Two more provider accounts publish through the actual API. The anonymous directory finds their three services.
3. An organizer signs up, creates a wedding template, removes unneeded service roles, edits notes and adds a checklist task. The remaining florist/caterer/band roles receive invitations.
4. Each provider explicitly accepts. Before acceptance the chat/history is hidden; after acceptance messages can be exchanged between separate accounts. Readiness becomes complete only at three current accepted roles.
5. A checklist completion preserves acceptances. Changing service scope invalidates them, removes provider chat/history from the UI and asks for renewed agreement. Logout removes private UI and the server returns 401 for protected access.
6. Both interface languages and themes stay usable at 375px. The date-comparison flow distinguishes booked profiles from still-eligible profiles displaced by returning candidates.

## Defects found and corrected during review

- **Stale offer acceptance:** editing a listing or replacing an invitation previously retained the old event revision. The review reproduced an old acceptance approving a changed offer. Both actions now advance the revision; stale responses/plan saves return 409. Unrelated accepted roles remain current, while the affected offer requires a fresh acceptance. Tests also verify that recipients see the current price and description.
- **Non-finite insights errors:** the mounted date-comparison app initially lacked the core JSON-safe validation handler. Three regressions first reproduced HTTP 500 for NaN/infinities, then passed with HTTP 422 after reusing the shared handler.
- **Provider price typing:** sequential `4e2` must not be silently converted to `42`. The listing editor now preserves rejected-edit state until an intentional correction, while an empty draft accepts a new valid digit. Price bounds, grouped values, paste, selection and mobile-style edits have regression coverage.
- **Theme/accessibility:** shared light/dark tokens fix earlier low-contrast hints/evidence. Header icons are centered SVGs; primary controls and interactive links have comfortable targets. Native optional working-language selection and the snapshot/date notice are retained when adapting Spectra's new layout.
- **Test-only corrections:** a component test tried to click New listing before templates enabled it; it now waits for readiness. A browser assertion incorrectly expected Send to be enabled for an empty chat draft; it now checks an enabled editor and disabled empty-message submission. Neither test was fixed by weakening application safeguards.

## Boundaries and human actions

The runtime is deterministic matching plus local collaboration, not an LLM agent. Source profiles have only an honest copyable inquiry; community accounts are unverified and separate. Chat uses periodic refresh and requires current membership. Identity/contact verification, bookings, payments, notification delivery, public hosting, production-scale storage and moderation/recovery/privacy operations are not claimed. [Community documentation](community.md) specifies the retained history and access rules.

GitHub Actions is manual-only because earlier organization billing restrictions prevented jobs from starting; local passes are not a green cloud CI claim. The captain must still rehearse, submit the correct repo/demo links and verify the submission receipt before the official cutoff. Team members must comply with the organizer's attendance rules. No implementation or checklist guarantees a jury score or prize.
